# 两条路线：把"操作用户电脑"补全 vs 做成客户端应用

写于 2026-09-17；**计划 B 于同日按用户澄清改写为"双模式客户端"**。两个计划**不互斥**，第 3 节给合并顺序。

- **计划 A（原计划）**：保持"循环在服务器、手在客户端"，把缺的能力一个个补进 `dsh-subprocess-dispatch` 的机器工具面。
- **计划 B（客户端应用，双模式）**：客户端一个窗口两种模式 —— **服务器模式**把现有 Web UI 搬进来（对话与资料留在服务器工作区），**本地模式**跑本地 agent 与本地工具（对话本地缓存并定时同步到服务器，文件经文件树手动上传）。服务器只新增**模型网关**；**浏览器直接使用服务端 agent 的能力原样保留**。

难度单位：**小**（半天内）／**中**（1–2 天）／**大**（3 天以上，含未验证的关键假设）。所有估计都含"写代码"，不含取证与回归（按本部署这一周的经验，取证常常和实现一样贵）。

## 1. 计划 A：在现有架构上补全（循环在服务器）

### A.1 现状盘点（已验证，不是推测）

| 已有 | 证据 |
|---|---|
| `machine_list` / `machine_run`：指名机器执行命令、超时杀进程树、执行器自报 `home`/`user` | `plugins/dsh-machine-probe`（真工具注册表按名字调用，6 步全过） |
| 执行器：SEA 单文件 exe + 旁挂 node-pty、部署密钥注册、machineId 寻址、状态页、`--self-test`、分发包端点 | 2026-09-16 打包线；2026-09-17 修掉"每结束一个终端多一个自己" |
| 通道能力：`proc.*`（进程 + 流 + spill + stdin 载荷）、终端（ConPTY）、`http.*`（客户端回环转发 + 端口白名单）、`bind.*`（保留但无 UI 入口） | `lib/client-transport.js`、`executor/executor.mjs` |
| 服务端：浏览器 + 服务器工作区（多账号授权、隐藏项、管理台） | `profiles/web-client`，线上 3080 |

### A.2 要补的每一项

| # | 功能 | 难度 | 技术缺口 / 风险 | 关键实现点 |
|---|---|---|---|---|
| A1 | `machine_read_file` / `machine_write_file` | 中 | WS 分块 + 背压；取消；Windows 错误分类（`EBUSY` 文件被 Office 占用、`EACCES`、`ENOSPC`、>260 字符长路径、中文名）；写入原子性 | 新帧 `fs.read.start/chunk/done`、`fs.write.start/chunk/end`；两端 sha256；临时文件 + rename；`mkdirs`；服务端 `dest`/`source` 走会话工作区并由 `sandboxPolicy` 收容；无 `dest` 且 >64KB 时**拒绝**并要求给 `dest`，不截断 |
| A2 | `machine_run` 加 `stdin` | 小 | 无（传输层已支持 `{data}` 载荷） | 一次性喂输入；`utf8`/`base64` 两种编码 |
| A3 | 后台长任务 `machine_job_start` / `_output` / `_kill` / `_list` | 中 | **任务的归属**（按会话隔离，别的会话不能杀）；**服务器/链路一断任务就死**（执行器 `abandon` 会杀自己名下的树）——这是语义，不是 bug，必须写清；输出上限与轮转 | 复用 `RemoteHandle` 的 spill（现在写到**服务器** tmp，天然给 `machine_job_output` 提供偏移读取）；服务端一张 job 表；`_output(jobId, offset)` 返回增量 |
| A4 | 交互式终端 `machine_terminal_open` / `_write` / `_read` / `_close` | 中 | 输出是流不是"行"：模型要轮询 + 空转检测（`sleep` 采样），没有提示符概念；每会话每机器一个终端，避免互相踩 | 传输层 `spawnTerminal` + `RemoteTerminalHandle` 已就绪，主要写注册表与工具；Ctrl-C 走 `signalForeground('SIGINT')` |
| A5 | `machine_screenshot` | 小～中 | DPI 缩放、多屏拼接、无交互会话时全黑、4K PNG 体积 | PowerShell + `System.Drawing` 截屏存 PNG → 复用 A1 拉回工作区 → 返回路径给 `read_image` |
| A6 | `machine_http`（客户端本地服务） | 小～中 | 白名单目前是**全局**不是按机器；响应体积上限；这是"能打通用户本机服务"的能力，安全面要写明 | 复用 `http.*` 转发机制，做成工具壳 + 白名单校验 |
| A7 | `machine_glob` / `machine_grep` | 中 | 忽略规则（`node_modules`/`.git`）、二进制跳过、结果上限与"被截断"提示、大目录并发上限 | 在执行器里用 Node 递归实现（**不依赖 ripgrep**，否则客户端又要装东西） |
| A8 | 权限与审批 | 小～中 | 现在的口径是"任何登录账号可驱动任何在线机器"；破坏性操作没有审批；接引擎的 `PreToolDecision.ask` 后，**headless/CLI 会话无人可点会挂住** | ① 配置级准入（按账号/按机器白名单）；② 破坏性工具走审批服务；③ 每次调用带账号 + 会话的审计行 |
| A9 | 提示词层 `machines:connected` + 机器能力清单 | 小 | 提示词每轮都进上下文，列太细烧 token；能力清单要缓存（一次探测，连接内复用） | 只列 别名/host/平台/登录用户；清单探测（注册表 + PATH：PS/Office/Blender/Python…） |
| A10 | 审计 | 小 | 日志含路径与命令（可能敏感）→ 保留期与可见范围 | 独立审计文件 + 轮转；复用 `tracePath` 机制 |
| A11 | `local-staging` skill 改写 | 小 | 该 skill 的触发条件引用了一段**已经渲染成空串**的提示词段，现在是死的 | 改成"本机目录签出 → 调软件 → 回写"，并修触发条件 |
| A12 | 机器别名进列表（顺手补的洞） | 小 | `hello` 里有 `label`，传输层**没保留**，所以人看不出哪台是哪台 | `describe()`/`machines()` 带上 `label` |

### A.3 计划 A 的固有限制（补不掉的部分）

1. **两份文件**：服务器工作区与客户端机器上的文件永远是两份，任何工作流都要显式搬运；几百 MB 的 PSD/Blender 走 WS 通道会很慢（需实测吞吐，同机 vs 跨机）。
2. **模型的心智负担**：agent 要一直分清"路径属于哪台机器""文件现在在哪一边"。
3. **能力永远差一截**：客户端的 shell/终端/文件不是原生工具（没有 LSP、没有引擎的沙箱语义、结果要过 socket）。
4. **逐台升级**：客户端每台都要换执行器包，且有版本协商问题。
5. 审批、配额、审计、按机器授权都得单独做。

**总量**：约 8–10 天实现 + 5 天左右取证与回归 ≈ **2–3 周**。

## 2. 计划 B：客户端应用（类豆包，双模式）+ 服务器保留 web

> 本节按 2026-09-17 用户第二次澄清改写：**客户端分"服务器模式"与"本地模式"**；服务器模式就是现有 Web UI 搬进客户端窗口（对话与资料留在服务器工作区）；本地模式用本地 agent 工具，对话本地缓存并定时同步到服务器，文件由用户经文件树手动上传到工作区。**浏览器直接用服务端 agent 的能力原样保留。**

### B.1 形态

```
                       客户端应用（一个窗口，两种模式）
      ┌───────────────────────────────────────────────────────────┐
      │ [服务器模式]  WebView → https://<服务器>:8443              │
      │                对话/文件/权限/文件树上传下载 = 全部照旧      │
      │                          ⇅ 模式切换（就是一个 URL 换另一个） │
      │ [本地模式]    WebView → http://127.0.0.1:<随机端口>/?token= │
      │                本地跑一份 dsh web（本地循环 + 本地工具）     │
      │                文件/shell/终端/截图/长任务全部原生          │
      └───────────────────────────────────────────────────────────┘
             │ 本地模式：模型请求（不带密钥）        │ 归档同步（定时）
             ▼                                      ▼
      ┌────────────────────────────────────────────────────────────┐
      │ 服务器：门禁/账号（dsh-remote-local，不变）                 │
      │         模型网关（新插件）→ 真 AI 接口（密钥不出服务器）     │
      │         工作区 / 文件树 / 会话 / 权限 / 管理台（全部不变）   │
      │         浏览器直接用服务端 agent（原样保留）                 │
      └────────────────────────────────────────────────────────────┘
```

**一句话**：服务端几乎不用动（只加一个模型网关），客户端把"本地模式"这一半带在身上。

### B.2 四条链路逐个评估

| 链路 | 能不能 | 靠什么 | 缺口 / 难度 |
|---|---|---|---|
| ① **服务器模式**：客户端里呈现现有 Web UI，对话与资料都在服务器 | ✅ **今天就能做，服务端零改动** | 外壳里一个 WebView 指向 `https://<服务器>:8443`；登录 cookie、文件树上传下载、会话列表全部照旧 | 自签证书：把 caddy 根证书装进**当前用户**证书库（不需要管理员），或外壳只信任这一张。**小** |
| ② **本地模式**：本地 agent + 本地工具 | ✅ 能，但要先把引擎搬过去 | 客户端跑自己的 `dsh web`（回环 + 一次性 token），profile = 基础组合 + 本地工具 + `llm` 指向网关 | 缺**打包**：dsh CLI + 引擎包 + 前端资源 + Node 运行时（前端外壳不是独立应用，**只有 `dsh web` 注入 `window.__DSH_BOOT__`**）。**B7 spike 决定一切**，中 |
| ③ **对话本地缓存 + 定时同步到服务器** | ✅ 能，但两种形式代价差一个量级（见 B.5） | 会话就是 `${DSH_HOME}/sessions` 下的 JSONL；上传到服务器某个目录不难 | "服务器上能**当会话读**" 与 "服务器上能**当历史查**" 是两件事；前者有版本锁与只读约束。中 |
| ④ **文件资料手动上传到工作空间** | ✅ **今天就能做，零新功能** | 切到服务器模式，用文件树插件已有的**上传**（拖拽/选择文件） | 想更顺（本地模式里一个"推送到工作区"按钮）= 调用同一个上传接口，**小**（可选） |

**结论**：这个设计里**真正新增的服务端功能只有模型网关**；工作区、文件、权限、上传下载、会话浏览全部复用现有能力。

### B.3 服务端要做的事

| # | 功能 | 难度 | 技术缺口 |
|---|---|---|---|
| B1 | **模型网关**：`/llm/v1/chat/completions`（SSE）+ `/llm/v1/models`，按用户 token 认证，转发到真 AI 接口 | 小～中 | 流式**取消要贯穿**（客户端断开 → 立刻 abort 上游，否则烧钱）；用量入账（流式下拿 `usage`）；每用户额度与并发上限；模型白名单；上游错误映射；密钥只在服务器 |
| B2 | 客户端 token 生命周期（签发/吊销/限额），复用执行器 token 那套存储与吊销路径 | 小 | 删账号要连带吊销；token 泄漏的止损（限额 + 审计） |
| B3 | 客户端版本与更新清单服务（复用分发包端点 + Range 续传） | 小～中 | **版本矩阵**：应用版本 ↔ 网关协议版本 ↔ 会话格式版本；强制升级策略；回滚 |
| B4 | 用量统计与额度视图（管理台一页） | 小 | 现有统计页统计的是会话，不是 token |
| B5 | **（可选，形式 1 才需要）** 本地会话导入端点：接收客户端会话 JSONL，放进某工作区并重建索引，标成"来自客户端（只读）" | 中 | 见 B.5 的三条硬约束 |
| B6 | 保留 web 形态 | 小 | 两条路共享账号/额度/管理台，需要一层统一的"这人能用哪些模型、多少额度" |

### B.4 客户端要做的事

| # | 功能 | 难度 | 技术缺口 |
|---|---|---|---|
| B7 | **打包可行性 spike（必须先做）** | 小 | 今天只验证过**执行器**（一个小 `.mjs`）能打成 SEA。`dsh web` 要带 **dsh CLI + 引擎包 + 前端资源 + Node 运行时**。SEA 对动态 import/资源加载的限制**未验证**；备选是"目录分发 + 安装器摆放"。**这个结论决定 B 是 2 周还是遥遥无期** |
| B8 | 客户端 profile（本地循环 + 本地工具 + `llm` 指向网关） | 小 | **默认全权限（用户已定，2026-09-18）**：设 `danger-full-access`、无审批 —— 代价是 agent 以该 Windows 用户身份无阻拦操作，安装时必须向用户说明；"阉割 AI 访问" = 不配 key、不装 provider 选择界面 |
| B9 | 外壳：窗口 + **模式切换** + 证书信任 + 凭据存储 + 模式标识 | 中 | **Electron（用户已定，2026-09-18）**：主进程拉起本地 `dsh web`（随机回环端口 + 一次性 token），BrowserWindow 承载两个 URL（服务器模式 / 本地模式）；证书走 Chromium 校验钩子或装当前用户根证书；凭据进 `safeStorage`（DPAPI）；**两个模式必须一眼可分**，否则用户会以为自己在服务器上操作 |

| B11 | 更新通道（应用内自更新） | 中 | "运行中不能覆盖 exe" → 先退出再替换（或 `.new` + 重启替换）；断点续传；失败回滚；Electron 可用 `electron-updater`，也可以复用执行器那套"服务器发清单 + Range 续传" |
| B12 | presets / skills 的来源 | 小～中 | 服务器侧有 279 个角色 preset 与全局 skills。**打包一份**（改了要重发安装包）还是**登录后从服务器拉**（需要同步接口与版本号） |
| B13 | 本机回环 API 的访问控制 | 小 | 本地 `dsh web` 若不做校验，**同机任何进程都能驱动 agent 并烧模型额度**。做法：一次性 token 启动（引擎本来就发）+ 随机端口 + 网关 token 只经环境变量注入、存 DPAPI |
| B14 | 本地会话的归档导出器 | 小 | 把会话导出成 Markdown/JSON，**带账号与机器标识**；失败重试；断网时排队 |

### B.5 对话同步的两种形式（**已定：形式 2**，2026-09-18）

用户拍板：**归档成文档、按账号上传到服务器**，服务器随后用 AI 精简并写进 Obsidian。因此不选形式 1，**没有会话格式版本锁**（B.6 第 1 条随之消失）。

| | 形式 1：同步成"服务器上的会话"（**未选**） | 形式 2：同步成"归档/文档"（**已选**） |
|---|---|---|
| 做法 | 客户端上传会话 JSONL，服务端插件放进某工作区的会话目录并重建索引 | 客户端把对话导出成 Markdown/JSON，**按账号**上传到服务器；服务器用 AI 精简后写进 Obsidian |
| 服务器上怎么看 | 会话列表里点开，像普通会话一样读 | 在 vault 里按笔记读（原始归档另存一份） |
| **能不能继续/分叉** | ❌ **不能**：会话里记的 `cwd` 是**客户端本地路径**，服务器上没有这些路径，续跑/分叉会立刻跑歪 → 只能是**只读历史** | 本来就不是会话，没有这个问题 |
| 硬约束 | ① 客户端与服务端的会话格式版本必须兼容（不认识的类型会拒绝整份日志）→ 客户端不能随便比服务器新；② 只读标记必须实做；③ 需要分辨"这条会话来自哪台机器" | 无版本耦合；但需要"按账号"的落盘位置、去重规则、以及精简产物的质量把关 |
| 难度 | 中 | 小（导出 + 上传）+ 中（服务端精简与落库，见 B16） |

### B.6 计划 B 的固有限制

1. **版本锁**：本地会话要能被服务器读，客户端与服务器的引擎版本必须兼容 —— **以后不能单独升级服务端**。这是这个设计最长期的纪律成本。
2. **服务端治理盲区**：本地模式里 agent 在客户端做了什么，服务器**看不到**（只看到 token 消耗）；本地审计只能靠客户端自报，可被篡改。
3. **数据不集中（本地模式）**：本地模式的工作区在各自电脑上，服务器的授权/共享/备份体系对它们无效；要靠 ③④ 手工回传。
4. **服务器模式的能力回退**：服务器模式里 agent 的工具在服务器上跑，**要驱动用户本机的 Photoshop/Office 仍得靠执行器**（计划 A），否则只能"下载 → 本地改 → 上传"手工往返。
5. **体积与更新**：**全量包 300–600MB**（用户已定），且每次改工具都要逐台更新。
6. **模式误认**：用户在本地模式里以为自己在服务器上操作，是这个设计最容易出的事故 → 必须有强视觉区分。
7. **全权限的后果**：本地模式无审批、无沙箱，agent 以该 Windows 用户身份可以动这台机器上的任何东西 —— 不是缺陷，是用户的选择，但必须在安装引导里说清。
8. ~~版本锁~~：**已消失**（选了形式 2，不再要求客户端会话格式与服务器兼容）。

| v2（增强） | 额度/用量台、"推送到工作区"按钮、presets 从服务器拉、归档增量去重 | 再 3–5 天 |

## 3. 建议的合并顺序（按改写后的计划 B 更新）

改写之后，**计划 B 的本地模式把计划 A 的大部分动机消掉了**：文件、长任务、终端、截图、本机服务在本地模式里全是原生能力，不需要通道、不需要执行器。计划 A 仍然有它的位置 —— **没装客户端的机器**，以及**服务器模式 + 本机软件**（服务器工作区的文件要在用户电脑上的 PS/Office 里处理）。

| 阶段 | 做什么 | 为什么是这个顺序 | 产出 |
|---|---|---|---|
| 0 | **B7 spike**：`dsh web` 的可分发打包 | 一天内出结论，决定 B 的体积与可行性 | 可行/不可行 + 体积、启动时间 |
| 1 | **B1 模型网关** + 客户端 profile → 本地模式连上服务器模型跑通 | 小、独立、只此一件服务端新功能；当天可验证"本地循环 + 远程模型" | 一条真实链路 + 用量视图 |
| 2 | 外壳：双模式切换 + 证书信任 + 凭据 + 模式标识 | 到这一步用户就能"像豆包一样用"了 | 可用的客户端应用（手工安装） |
| 3 | B14 归档导出/上传（按账号）+ B16 服务端精简 → Obsidian | 补上"对话与资料最终落到服务器"；**用户已定形式 2** | 数据回流闭环 |
| 4 | B10/B11 安装器 + 自更新（**全量包**） | 交给不懂技术的用户的前提 | 可分发的安装包 |
| 5 | 按需：A 的 P0（文件/stdin/后台任务） | 只有"要给没装客户端的机器操作用户电脑"或"服务器模式要驱动本机软件"时才做 | 现有形态下的完整能力 |
| 6 | 按需：额度台、presets 从服务器拉、归档增量去重 | 增强 | —— |

**一句话结论**：
- **计划 A**＝"把裂缝补上"：2–3 周，**能力完整但仍浏览器形态**，服务端改动大（通道 + 一堆工具）。
- **计划 B（改写后）**＝"把裂缝取消"：2–3 周，**App 体验 + 服务端几乎不动**，代价是本地模式的版本锁、治理盲区，以及安装/更新的长期成本。
- **先做阶段 0 与 1**：两件都不需要动现有部署，也不需要先拍安装包体积。
